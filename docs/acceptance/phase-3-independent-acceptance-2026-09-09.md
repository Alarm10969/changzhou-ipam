## 4. 缺陷

### F-01（阻断/P0）：合法 PC 申请返回系统内部错误

**复现步骤**

1. 科技管理员依次选择支行、网点、科技资产、PC 小类。
2. 填写使用人姓名和统一认证号，不填写资源编码。
3. 提交申请。

**实际结果**：HTTP 500，页面提示“系统内部错误，请联系管理员”。

**期望结果**：PC 不要求资源编码，申请正常进入待审批。

**根因证据**：服务层按新规则允许 PC 的 asset_code 为空，但 V004 创建的 ip_application 仍保留旧约束：科技资产必须同时具有非空 asset_code 和 device_type。V010 至 V012 增加了新字段，但没有重建该表或更新旧 CHECK 约束，导致合法 PC 数据在数据库层被拒绝。

**影响**：PC 是明确要求支持的科技资产类型，该申请链路完全不可用，属于正式交付阻断项。

### F-02（重要/P1）：资源池编辑状态回显为“可用”

**复现步骤**

1. 将普通可用 IP 108.56.1.98 改为“人工保留”，填写“独立验收人工保留”并保存。
2. 列表确认该 IP 已显示“人工保留”。
3. 再次点击“编辑状态”。

**实际结果**：状态下拉框显示“可用”，说明仍保留“独立验收人工保留”。

**期望结果**：下拉框应回显“人工保留”。

**根因证据**：当前启用的 poolV2 编辑弹窗固定按“可用、停用、人工保留”输出选项，没有根据 item.state 设置 selected。

**风险**：管理员仅查看后误点保存，即可能把人工保留或停用 IP 错误改成可用，存在资源误分配风险。

### F-03（重要/P1）：已处理申请明细不满足需求基线

**实际结果**：已通过申请的详情仅展示申请人账号、资产、一个条件字段、推荐/最终网段、最终 IP 和审批人；同时只读弹窗仍显示“保存修改”。

**缺失内容**：申请人姓名、申请时间、支行/网点、完整条件字段、审批时间、审批意见。PC 场景还需同时展示使用人姓名和统一认证号。

**需求依据**：docs/requirements-change-baseline-2026-09-04.md 第 176 行要求已处理申请展示申请人、申请时间、资产大类/小类、条件字段、推荐网段、最终网段、分配 IP、审批人、审批时间和审批意见。

**影响**：管理员无法在系统内完整追溯审批依据和结果，审批历史验收项不通过。

### F-04（一般/P2）：审批完成后待审批角标未即时刷新

**实际结果**：审批成功、待审批列表已为空后，左侧“申请审批”角标仍显示 1；重新进入概览或刷新后才会更新。

**期望结果**：审批或驳回成功后同步更新角标，避免误导管理员。
